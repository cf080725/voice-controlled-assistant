# 决策记录 001：不部署现有的 LoRA 微调意图模型

- 日期：2026-10-06
- 状态：已决定（继续使用原版 Qwen2.5-1.5B-Instruct，即 `canaan-desk:1.5b`）
- 相关：docs/EVALUATION.md 第 1.6 节；`tools/intent_eval_report.py`、`tools/compare_intent_models.py`

## 背景

审计时发现，一直以为是“微调模型”的 `canaan-desk:1.5b` 与 `qwen2.5:1.5b` 是 Ollama 中的同一份权重（同一个 blob），`canaan-desk:7b` 与 `qwen2.5:7b` 也一样。也就是说，此前所有的意图识别数字都来自“原版模型 + 系统提示词 + 规则”。

仓库里确实有训练过的 LoRA 合并模型（`canaan_commercial_model`、`_v3`、`_v4`、`training_suite/merged_canaan_model`，均为 Qwen2.5-1.5B），但从未转换、导入或评测过。问题是：要不要换上它们？

## 做了什么

1. 取最新的两个（`canaan_commercial_model_v4`，2026-10-01；`training_suite/merged_canaan_model`，2026-10-02），用 llama.cpp b6500 的 `convert_hf_to_gguf.py` 转为 F16 GGUF，再用 `llama-quantize` 量化为 Q4_K_M（与原版同样的量化），导入 Ollama 为 `canaan-ft-v4:1.5b`、`canaan-ft-merged:1.5b`。
2. 三套用例同一流程评测（规则通道 + 大模型 + 防误执行守卫）：
   - dev（210 条，规则对着它写的）
   - dev2（89 条，“提到≠命令”，调参用）
   - unseen（125 条，测试集，从未用于调参）
3. 两种口径：只用单个模型；以及实际部署方式（JSON 格式不对时依次换 qwen2.5:1.5b → 7B）。

## 数据

单独使用：

| 模型 | unseen 正确率（95% CI） | 大模型路径 JSON 无效 | 首选模型一次成功的延迟 P50 / P90 |
|---|---|---|---|
| 原版 | 56.0%（47–64%） | 46.2% | 0.18s / 0.48s |
| ft-v4 | 62.4%（54–70%） | 21.6% | 0.37s / 0.99s |
| ft-merged | 74.4%（66–81%） | 15.9% | 0.70s / 1.05s |

实际部署方式：

| 首选模型 | dev | dev2 | unseen（95% CI） | 错误执行（unseen） | JSON 无效 | 回退到 7B | 大模型路径延迟 P50 / P90 |
|---|---|---|---|---|---|---|---|
| 原版（现部署） | 91.9% | 93.3% | 72.8%（64–80%） | 14 | 9.6% | 56/208 | 2.18s / 27.7s* |
| ft-merged | 91.0% | 95.5% | 73.6%（65–81%） | 18 | 1.0% | 18/208 | 0.94s / 1.42s |

\* 本次运行时显存里同时驻留了多个 1.5B 模型，回退 7B 时发生换入换出，长尾被放大。正常运行时回退一次约 5~8 秒。

显存：两者都是 Q4_K_M，约 1.2GB。

## 取舍

微调模型的好处是真实的：它学会了输出格式（JSON 无效 9.6% → 1.0%），回退到慢得多的 7B 的次数减少三分之二，因此长尾延迟大幅下降。

但用户真正关心的是“说的话能不能被听懂”。在部署方式下，未见说法上的正确率两者持平（73.6% 对 72.8%，区间几乎重合），错误执行反而略多（差异在噪声内）。同时微调模型每次输出更长（带代码块和长回复），**首选模型一次成功时的典型延迟从约 0.18s 变成约 0.94s**——这是每一句话都要付的代价，而 7B 长尾只出现在少数句子上。

## 部署标准

只有同时满足以下条件才替换：
1. 在 unseen 测试集上的正确率高于现部署方案（区间不重合，或在多次运行中稳定更高）；
2. 指令判断的典型延迟（P50）不变差，长尾（P90）不变差；
3. 错误执行次数不增加。

ft-merged 只满足“长尾更好”，不满足 1 和 2，因此**不部署**。
